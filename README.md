# modular-architecture v2

高内聚、低耦合、可插拔；先模块/接口/主流程骨架，再具体实现和测试。

这是原 modular-architecture 的升级版，不是第二个需要同时启用的 Skill。名称和调用方式不变。
本版本新增流程图驱动的新项目开发与既有项目增量修改；原架构约束保留。
这是纯指令型技能，不含自动安装或执行脚本，不新增图片工具或权限。

## 文件分工

- SKILL.md：入口判断、公共架构约束和通用开发流程。
- references/flowchart-development.md：需要按图开发时才读取的详细步骤。
- assets/flow-spec.template.md：按需生成项目流程规范、架构和代码/测试映射的模板。
- README.md：安装、使用和升级说明；不需要每次开发都读取。

流程图和项目业务数据放在你的项目中，不放入共享 Skill。
文档里的节点 ID、项目路径和测试名示例不代表真实项目已经存在。

## 安装或升级

将压缩包里的整个 modular-architecture 目录放到以下位置之一：

当前项目：

```text
<项目根目录>/.agents/skills/modular-architecture/
```

多个项目共用：

```text
~/.agents/skills/modular-architecture/
```

用户目录指实际运行 Codex 的环境中的用户主目录。
升级时先备份旧目录到技能扫描目录之外，再复制新版；存在你自行修改的规则时先比较并合并，不盲目覆盖。
不要只复制 SKILL.md：本版本会引用 references 和 assets 内的文件。
不要同时保留两份同名的新旧 Skill；Codex 不会自动合并同名技能。
也不建议为了备份而把旧目录改名后继续留在 .agents/skills 中，因为其 SKILL.md 的 name 仍可能相同。
Codex 会自动检测技能变化；未出现时再重启 Codex，并用 /skills 或输入 $ 检查。

## 新项目：先审阅方案

以下是发给 Codex 聊天框的消息，不是终端命令；示例图路径请替换成你的真实路径。

```text
$modular-architecture

这是一个全新的项目，请根据 docs/flows/main.mmd 开发。
采用高内聚、低耦合、可插拔原则，先骨架，再实现。

先读取流程图，复述节点、条件、分支与异常路径，列出缺口和假设。
不要把每个节点机械拆成模块。
输出模块边界、关键接口、主流程骨架、实现组装位置和分阶段计划，
建立流程节点/分支到代码和测试的计划映射。
本次只给方案，不创建或修改业务代码；等我确认后再实施。
```

审阅后可以这样继续：

```text
按已确认的流程规范和架构方案完成第 1 阶段。
保持核心业务依赖接口，先骨架再接入真实实现。
同步更新流程映射，运行测试，区分替身验证与真实集成。
仅完成第 1 阶段，不进入后续阶段或部署生产。
```

## 旧项目：

```text
$modular-architecture

这是一个已有项目，请在现有代码基础上增量修改，
不要按新项目重新初始化或重建架构。

本次需求：
【填写要新增、修改或修复的内容】

先阅读相关代码、调用链、配置、测试和当前工作区改动，
说明现有实现、本次影响范围，以及需要保留的接口和行为。

遵循高内聚、低耦合、可插拔：
先给出本次修改涉及的模块、接口和主流程骨架，
再完成实现与测试。

沿用现有技术栈与工程约定。
不修改无关模块，不覆盖我已有的改动。
只有存在真实变化点时才增加抽象，不强行插件化。

没有流程图时，依据需求和现有代码推进，不要求补图。
小改动简化流程，不生成无必要的架构文档。

说明方案后继续完成本次修改。
最后报告修改位置、兼容性影响、
实际执行的测试及尚未验证的部分。
```

## 理解代码

```text
$modular-architecture

本次任务：只读理解现有代码，不是开发、修复或重构。

请先帮我理解当前项目。
先还原模块、接口和主流程骨架，再解释关键实现。
不要一开始逐行翻译所有代码，也不要只列目录名称。

按以下顺序讲解：

1. 项目是做什么的，主要入口在哪里，核心模块各负责什么。
2. 选择一条具有代表性的业务主流程，
   从入口追踪到最终结果，说明调用关系和数据变化。
   如果我指定了功能，则优先追踪该功能。
3. 解释这条流程里的关键函数：
   输入、输出、主要步骤、条件分支、异常和副作用。
4. 说明接口与具体实现的关系，
   配置如何选择实现，依赖在哪里创建和传入。
5. 最后给出建议阅读的关键文件、函数和阅读顺序。

讲解要求：
- 先用通俗语言说明作用，再结合实际代码解释。
- 重要结论标出实际文件路径和函数名；
  能确认行号时附行号，不要编造位置。
- 区分代码中已确认的事实、推断和未验证的运行行为。
- README、注释与代码不一致时，指出差异。
- 没有读到实现时，不要只根据函数名猜测行为。
- 大项目先梳理主干，明确已阅读范围，不声称读完所有代码。

边界要求：
- 不修改、新增或删除任何项目文件，包括注释和文档。
- 默认只读取、搜索和静态分析。
- 不自行启动服务、运行项目脚本或测试、安装依赖。
- 不自动修复问题或重构代码。
- 发现与理解当前流程有关的重要问题，可以单独说明，
  但不要让架构改造建议取代代码讲解。

本次直接在回复中解释，不把分析写入项目。
```

用户已经授权完整实施时，不需要每一步重复确认；保留用户指定的确认点即可。

## 按更新后的流程图修改既有项目

```text
$modular-architecture

对照 docs/flows/main-v2.mmd 和现有实现，列出新增/删除节点、
分支条件和状态迁移的变化，然后按本次需求增量修改。
保留未受影响的行为，更新流程到代码/测试的映射，执行受影响的回归。
不重建整个项目，不静默修改原图来适配现有代码。
```

## 没有流程图或只做架构评审

仍可按原来的方式使用技能；不强制创建流程图，也不重跑新项目初始化。
例如：`$modular-architecture 评审当前模块依赖和可插拔边界，本次不要改代码。`

## 输入建议和限制

可编辑源文本有助于核对节点、分支和后续变更；也可提供清晰图片。
具体的图片、PDF、SVG 或 draw.io 文件能否读取，取决于当前 Codex 环境提供的工具。
无法读取或看不清的部分应明确报告，不得猜测。
如果图中没有技术栈、超时、重试或权限细节，Codex 应区分已知规则、可逆工程假设和必须解决的业务缺口。
Skill 是开发指令，不是图到代码的编译器，不保证自动生成的实现与图完全等价；需要代码审查和实际测试。
