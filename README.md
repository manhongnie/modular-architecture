# modular-architecture v3.0

**主要用于已有项目的代码理解、问题排查和增量修改；少数新项目任务按需切换。**
高内聚、低耦合、可插拔；先看清现有骨架，再设计本次变化，最后实现与回归。

## 本次实际变更

这是重写后的 v3，不是原样提取的 v2，也不是只有版本号变化。
主文件的 description、模式入口和默认执行流程均已改写；新增只读理解与新项目引用文件，同步修正流程图规则和模板。
具体变化见 [CHANGELOG.md](CHANGELOG.md)。技能 name 保持 modular-architecture，不另装一份同名 Skill。

## 文件分工

```text
modular-architecture/
├── SKILL.md                         # 默认规则；已有项目七步修改流程
├── references/
│   ├── code-understanding.md        # 只读理解：先全貌、再主链、再实现
│   ├── flowchart-development.md     # 按图理解或修改，不改变授权模式
│   └── new-project.md               # 仅真正从零开发时读取
├── assets/
│   └── flow-spec.template.md        # 按需使用；旧项目包含现状/目标/差异
├── README.md
└── CHANGELOG.md
```

没有图也能用；新增接口或模块不等于新项目。小 Bug 修复不强制抽象、画图、设计全项目或生成文档。
解释和评审默认不改文件；运行验证不能从“读代码”请求自动推导。
本包不含执行/安装脚本，不增加工具和权限，也不能保证模型每次严格遵守所有指令。

## 新项目：先审阅方案

以下是发给 Codex 聊天框的消息，不是终端命令；示例图路径请替换成你的真实路径。

```text
$modular-architecture

这是一个全新的项目，请根据 docs/flows/main.mmd 开发。
采用高内聚、低耦合、可插拔原则，先骨架，再实现。

先读取流程图，复述节点、条件、分支与异常路径，列出缺口和假设。
不要把每个节点机械拆成模块。
输出模块边界、关键接口、主流程骨架、实现组装位置和分阶段计划，
建立流程节点/分支到代码和测试的计划映射。
本次只给方案，不创建或修改业务代码；等我确认后再实施。
```

审阅后可以这样继续：

```text
按已确认的流程规范和架构方案完成第 1 阶段。
保持核心业务依赖接口，先骨架再接入真实实现。
同步更新流程映射，运行测试，区分替身验证与真实集成。
仅完成第 1 阶段，不进入后续阶段或部署生产。
```

## 旧项目：

```text
$modular-architecture

这是一个已有项目，请在现有代码基础上增量修改，
不要按新项目重新初始化或重建架构。

本次需求：
【填写要新增、修改或修复的内容】

先阅读相关代码、调用链、配置、测试和当前工作区改动，
说明现有实现、本次影响范围，以及需要保留的接口和行为。

遵循高内聚、低耦合、可插拔：
先给出本次修改涉及的模块、接口和主流程骨架，
再完成实现与测试。

沿用现有技术栈与工程约定。
不修改无关模块，不覆盖我已有的改动。
只有存在真实变化点时才增加抽象，不强行插件化。

没有流程图时，依据需求和现有代码推进，不要求补图。
小改动简化流程，不生成无必要的架构文档。

说明方案后继续完成本次修改。
最后报告修改位置、兼容性影响、
实际执行的测试及尚未验证的部分。
```

## 理解代码

```text
$modular-architecture

本次任务：只读理解现有代码，不是开发、修复或重构。

请先帮我理解当前项目。
先还原模块、接口和主流程骨架，再解释关键实现。
不要一开始逐行翻译所有代码，也不要只列目录名称。

按以下顺序讲解：

1. 项目是做什么的，主要入口在哪里，核心模块各负责什么。
2. 选择一条具有代表性的业务主流程，
   从入口追踪到最终结果，说明调用关系和数据变化。
   如果我指定了功能，则优先追踪该功能。
3. 解释这条流程里的关键函数：
   输入、输出、主要步骤、条件分支、异常和副作用。
4. 说明接口与具体实现的关系，
   配置如何选择实现，依赖在哪里创建和传入。
5. 最后给出建议阅读的关键文件、函数和阅读顺序。

讲解要求：
- 先用通俗语言说明作用，再结合实际代码解释。
- 重要结论标出实际文件路径和函数名；
  能确认行号时附行号，不要编造位置。
- 区分代码中已确认的事实、推断和未验证的运行行为。
- README、注释与代码不一致时，指出差异。
- 没有读到实现时，不要只根据函数名猜测行为。
- 大项目先梳理主干，明确已阅读范围，不声称读完所有代码。

边界要求：
- 不修改、新增或删除任何项目文件，包括注释和文档。
- 默认只读取、搜索和静态分析。
- 不自行启动服务、运行项目脚本或测试、安装依赖。
- 不自动修复问题或重构代码。
- 发现与理解当前流程有关的重要问题，可以单独说明，
  但不要让架构改造建议取代代码讲解。

本次直接在回复中解释，不把分析写入项目。
```

用户已经授权完整实施时，不需要每一步重复确认；保留用户指定的确认点即可。

## 升级

解压后，将整个 modular-architecture 文件夹放到所选安装位置，不只换 SKILL.md：新增引用文件必须一起复制。

多项目共用的用户级目录：

```text
~/.agents/skills/modular-architecture/
```

仅当前项目：

```text
<项目根目录>/.agents/skills/modular-architecture/
```

用户目录是实际运行 Codex 的环境的 HOME；不要把 Windows 主机和 Linux/WSL 用户目录混为一处。
先把旧目录备份到技能目录之外，再安装新版；有自定义改动先比较合并，不盲目覆盖。
不要把旧版仅改个目录名后继续放在扫描目录中，其 name 仍可能与新版重复。
Codex 可检测技能变化；没有出现新版时重启 Codex，再用 `$` 或 `/skills` 检查。

确认装入的主文件版本，可以在安装环境中执行（只检查文件内容，不证明已被 Codex 加载）：

```bash
grep -n '版本：3.0' ~/.agents/skills/modular-architecture/SKILL.md
grep -n '默认开发主流程：已有项目增量修改' ~/.agents/skills/modular-architecture/SKILL.md
```

## 常用：直接修改旧项目

下面是发给 Codex 的消息，不是终端命令。

```text
$modular-architecture

请修复当前项目中的【具体问题】，保持相关旧接口兼容。
```

不必每次重复一大段“不是新项目、不要重建架构”；这些已写进主文件。

## 常用：只读理解或排查

```text
$modular-architecture

帮我看懂【功能或文件】。先还原入口、模块和主调用链，再解释关键实现。
本次只读，不修改文件、不启动服务或测试。
```

```text
$modular-architecture

分析这个报错的原因，先静态排查，不修改代码。
区分已确认原因、推断和需要运行验证的部分。
```

明确要求“修复并测试”时才进入相应实施范围；明确授权有限运行验证时也仍受工具权限和环境边界约束。
