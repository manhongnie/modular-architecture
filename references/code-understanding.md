# 只读代码理解：先还原骨架，再解释实现

本文件补充 SKILL.md 的理解模式，适用于看旧代码、追调用链、解释模块和函数。
理解不是修改授权，也不等于必须评审全项目。按用户问题限定阅读和输出范围。

## R0. 明确阅读目标与只读边界

用户指定某个功能、文件或报错时围绕它展开；问整个项目时先找入口与一条代表性业务链。
读取适用指令与相关代码，默认只做静态分析。不新增/修改/删除项目文件，包括注释和分析文档。
不自行 import 业务模块、运行项目脚本、测试、服务、生成器或迁移，不安装依赖。
用户明确要求运行追踪时，先检查执行方式、环境与副作用，在授权范围内验证；不会因为“只读分析”而自动安全。
用户要求写分析文档时，只授权相关文档产出，不因此获得业务代码修改权限。

## R1. 先看全貌，但不遍历所有实现

核对构建/依赖配置、启动命令或入口、路由/命令注册、业务模块、配置和相关测试。
README、目录与注释提供线索，重要行为回到代码核对。
先回答项目解决什么问题、当前问题的入口在哪、哪些模块相关、各自负责什么。
不逐行翻译全部文件，不只打印目录树。没有语言框架入口时可以从用户指定调用点或库的公开 API 开始。

## R2. 沿一条真实主链追踪

按真实调用记录“调用方 → 公开契约 → 当前配置选择的实现 → 结果返回/状态变化”。
核查路由、注册表、工厂、构造参数和调用位置，不能只靠类名判断运行时选择了谁。
动态加载、反射或远端实现无法静态确认时，明确已知边界与待核对配置，不补造下游细节。
记录入口参数如何校验/转换、哪些规则决定分支、何时读取或写入、结果/异常如何返回。
同步调用、异步任务、事件与回调分开说明，不能把异步提交画成已经执行完成。
有缓存、持久化、外部服务、模型加载等时，仅展开对本次理解重要的部分。

## R3. 再解释关键实现

对每个核心函数优先讲：它解决什么、谁调用、输入/输出、关键判断、失败语义与副作用。
只有关键片段或用户明确要求时才逐行解释，不把整文件复述一遍。
结合一个简短输入示例说明数据如何变化；示例必须标为示例，不当作真实运行日志。
区分业务错误、依赖错误和配置错误；“捕获异常”不等于“正确恢复”，返回成功要追到实际产生结果的位置。
字段、状态和对象需解释业务含义，不只解释语法。

## R4. 用架构原则观察现状，不自动改造

高内聚：规则与状态目前归属哪里，是否有跨模块散落的职责。
低耦合：调用是否经公开契约，是否有共享可变状态或跨模块私有访问。
可插拔：实际存在什么接口，实现在哪选定和注入；切换哪些配置或代码才能替换，存在哪些语义和数据限制。
没有接口就如实说直接依赖具体实现；不要凭空发明一个 Provider、Repository 或“领域层”。
先描述现实，再单独给少量与理解有关的问题和建议；建议中的目标结构不能画成既有结构。
不要求读者先完成重构才可以看懂项目。

## R5. 给可核对的讲解与阅读路线

默认输出顺序：

1. 项目/功能作用与本次阅读范围。
2. 相关模块、实际入口和一条主调用链。
3. 关键实现及一个注明为示例的数据流。
4. 配置、状态/资源归属、依赖和替换边界。
5. 关键文件/函数的阅读顺序，以及未确认部分。

小问题可以只回答相关部分，不强制五段长报告。先通俗说明作用，再解释必要术语与代码细节。
重要结论标实际路径与函数；行号能核实才给。计划路径、推测文件和文档意图不标成已存在实现。
区分：源代码可确认、配置/条件成立时才会发生、合理推断、未执行验证。
文档、注释、测试与实现冲突时列出差异，不用“文档这样写”证明运行一定如此。
对于不可达代码、复杂并发顺序或外部服务状态，静态分析不足就明确限制。
除非要求落盘，讲解只在回复中给出。发现问题不自动修复，不宣称代码经过测试。
